# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static HTML prototype for **CanSpot** (internal `<title>`: "EnergyBoost — Prototyp"), a German-language mobile-first price-comparison app for energy drinks. There is no build step, no package manager, and no backend. `index.html` contains all CSS, inline SVG icons, and JavaScript in one file; it loads its offer data at runtime from [`deals.json`](#datenquelle-dealsjson) instead of embedding it inline.

## Running / previewing

No build or install step — open the HTML file directly, or serve it locally. A dev server config already exists at `.claude/launch.json`:

```bash
python3 -m http.server 8123
```

(matches the `canspot-preview` launch config, serving the current directory on port 8123). There is no lint, test, or build command — this is plain HTML/CSS/JS with no tooling configured.

## Architecture

Everything lives in one file, in this order: `<style>` (CSS custom properties + component styles) → SVG `<symbol>` icon sprite → `<body>` markup (app shell, sheets/modals) → one `<script>` block with demo data and all logic.

**Theming**: CSS custom properties are defined on `:root` (light) and overridden under `:root[data-theme="dark"]`. Theme resolution (`light`/`dark`/`system`, from `localStorage["canspot-theme"]`) happens twice: once in a tiny inline `<script>` in `<head>` (sets `data-theme` before first paint to avoid a flash of the wrong theme) and again later via `applyTheme()` once the UI is interactive.

**Data model** (top of the main `<script>`) — `products`, `storeLogos`, `storeBranches`, and `deals` are declared as empty `let` placeholders and populated at runtime by `loadDeals()` (see [Datenquelle (deals.json)](#datenquelle-dealsjson) below), not as inline literals:
- `products` — catalog (id, name, brand, sizeMl, hotlinked image URL), from `deals.json`'s `products[]`.
- `storeLogos` / `storeBranches` — retailer logo URL and branch info (address, hours, geo), derived from `deals.json`'s `stores{}` map (keyed by store name — this dataset models exactly one branch per chain in the demo area, not multiple branches per chain).
- `deals` — runtime array: `deals.json`'s `offers[]` joined with product info via `buildDeals()`, plus a `pfand`/`packaging`/`units` fallback (`PFAND_FALLBACK`/`PACKAGING_FALLBACK`/`UNITS_FALLBACK`, used only if an offer omits them), `totalMl` (`sizeMl × units`, used for per-liter math so multipacks price correctly), `priceHistoryPoints` (dated price points — an offer's own `priceHistory` normalized if present, else a synthetically generated 90-day series via `genPriceHistory`; see **Preisverlauf** below), a derived `history` array (`priceHistoryPoints.map(p => p.price)`, kept for existing plain-number consumers like badges/averages), and a deterministic `checkedMinutesAgo` (via `hashStr`).
- `DEMO_TODAY` is a **fixed date** (currently `2026-09-01`), not `Date.now()` — all "days until expiry / days since start" logic (`daysUntil`) is relative to this constant so the demo data's validity windows stay consistent regardless of when the file is actually opened. Update this constant when the demo dates are rolled forward.

**State & rendering**: No framework — plain module-level `let` variables (`selectedBrand`, `favorites` (a `Set`), `radiusKm`, `viewMode`, `hideExpired`, etc.) hold UI state, mutated by event listeners attached directly via `addEventListener`/`querySelectorAll`. Each state change is followed by an explicit call to the relevant render function:
- `render()` — filters + sorts `deals`, rebuilds the `#deals` list (or shows an empty state), and also triggers `renderMap()`.
- `renderMap()` — draws the radial "map" view (store pins positioned by hashed angle + normalized distance, not real coordinates).
- `renderAlertsView()` — the "Alarme" tab (price-alert cards + computed favorite events).
- Views (list/map/alerts, and the profile/history/store-detail/location/filter/sort sheets) are all plain DOM containers shown/hidden — there is no router.

**Sheets/modals**: bottom-sheet overlays (`.overlay` + `.sheet`) are generic — `openSheet(id)` / `closeSheet(id)` toggle the `.open` class on any `#...Overlay` element. New sheets should follow the existing markup pattern (`.overlay > .sheet > .sheet-inner`, optional `.sheet-scroll` + `.sheet-footer` for tall/scrolling sheets).

**Persistence**: `localStorage` only, no server sync. Keys in use: `canspot-theme`, `canspot-alerts`, `canspot-name`, `canspot-email`, `canspot-avatar`, `canspot-notif-*`.

**Images**: product images and store logos are hotlinked directly from the official manufacturer/retailer websites (no local copies), with `onerror` handlers falling back to inline SVG data-URIs (`FALLBACK_IMG`, `STORE_FALLBACK_IMG`). This is called out explicitly in the in-app disclaimer text — preserve that disclaimer if the data source approach changes. An offer can optionally override the image for that specific deal via `offer.bundleImg` (a multipack/tray packshot, used for multipack offers where `units > 1` so the card shows the actual pack instead of a single can) — `buildDeals()` prefers it over `product.img` when present; absent (the default for every offer), behavior is unchanged. The product catalog itself (`products[].img`, used by the product-detail sheet and "Ähnliche Produkte") is never affected by `bundleImg` — it always shows the single-can shot.
  - **Deliberate exception — `images/bundles/`**: the favorite-heart button on a deal card sits fixed at the top-right of the thumbnail (`.thumb-frame .btn.fav`, no backdrop/shadow/frame by design — a solid backdrop circle was tried and explicitly rejected). Virtually every official multipack packshot places pack-count marketing directly in that exact corner (a printed "4/6/12/24 PACK" ribbon baked into the retailer's own product photo, a marketplace-injected badge, or simply the pack/tray photographed edge-to-edge with no margin anywhere to reposition around), so the heart would sit on top of the artwork no matter which corner it's pinned to or which raw hotlinked photo is chosen. Every `bundleImg` in `deals.json` is therefore, as of now, a locally-edited copy under `images/bundles/` (relative path, same `offer.bundleImg` mechanism as before) rather than a raw hotlink — this is a deliberate, blanket exception to the hotlinking policy above, specific to multipack packshots, not a reversal of it (every `products[].img` single-can photo and every store logo is still hotlinked, unchanged).
    - **Recipe, apply identically to any future bundle image**:
      1. Fetch the highest-resolution version of the source photo available (Amazon/REWE/other retailer image CDNs usually accept a size parameter in the URL — try a few before settling for a small default).
      2. **Decide whether the source needs background removal at all — don't assume a transparent PNG is already clean.** Check the alpha channel's own bounding-box corners (a few px inset, to skip antialiasing): if they're already transparent, the source is a properly-separated non-rectangular silhouette (some REWE assets are already correctly cut out this way) — do NOT re-run flood-fill on it; doing so re-derives the whole silhouette from scratch by color-matching alone, and any part of the *product itself* that happens to be plain white/background-colored *and* touches the image's outer background (a white box panel merging into a white studio backdrop, say) will get wrongly matched and erased too, since flood-fill has no way to know that region is "product" rather than "background" once their colors are identical and they're path-connected. This exact regression happened to a Monster Ultra 4-pack box panel after applying flood-fill unconditionally to every source "for consistency." If the bbox corners are instead already *opaque*, the source has a baked-in rectangular "lake" of un-removed background around/behind the actual (often tilted/isometric) product shot — REWE's own separation is not uniformly reliable across their catalog, unlike Amazon's always-opaque JPGs which always need step 3.
      3. For sources that DO need it: remove the opaque (usually white) background in two steps. First, a **corner-seeded flood-fill on the image composited onto a plain white background first** (not on the raw RGBA source directly) — `ImageDraw.floodfill` matches on all 4 RGBA channels, so seeding from a pixel that's already transparent (alpha 0) can never bridge to opaque background pixels (alpha 255) regardless of threshold or RGB similarity; compositing onto white before flood-filling makes any pre-existing transparency register as plain white too, restoring correct connectivity. **Keep the flood-fill threshold LOW (~5) rather than generous** — a higher threshold (20-25 was tried) can bridge *through* fine detailed dark artwork (a logo made of thin black strokes on white, e.g. a "claw mark" graphic) whenever the true outer background is connected to the artwork's white gaps by any path of similarly-toned pixels along a receding/angled edge, silently carving a large chunk out of the *product's own graphic* — this rendered as a spreading black "drip"/smear over what should have been clean white panel, and cost a full extra debugging round because every symptom pointed at the resize step instead (see below). A low threshold undershoots on fringe cleanup, but that gap is covered by the border-zone step next, which doesn't depend on the flood-fill threshold at all. Second, the border-zone cleanup: dilate the resulting transparent mask by a couple of pixels, and within *that zone only* clear remaining bright/whitish pixels (mean RGB above ~200) — a plain flood-fill alone reliably leaves a ragged, speckled light fringe on small/JPEG-compressed sources (compression ringing around high-contrast edges isn't one connected region). Restricting the brightness cut to the dilated border zone (not globally) avoids eating into legitimate light product artwork further inside the image. For sources skipped in step 2, still run this border-zone cleanup pass alone (cheap, and catches any stray fringe without touching the good silhouette).
      4. Pad the canvas with extra transparent margin, top-heavy (roughly 3-4× more on top than bottom), sized so the top margin ends up at **≥30% of the final canvas height** — the number that clears `.thumb-frame .btn.fav`'s footprint (top-right ~25% height × ~30% width of the rendered thumbnail) with a safety buffer.
      5. Before resizing, extend the opaque product's edge colors outward into the surrounding transparent area (iteratively propagate each opaque pixel's RGB into its still-transparent neighbors, alpha untouched, ~12-15 iterations) — cheap insurance against Pillow's `resize` interpolating R/G/B and alpha independently ("straight", not premultiplied) at a padding boundary. **This step does NOT fix flood-fill leaks from step 3** — don't reach for more resize/premultiplication tricks (extend-color, manually premultiplied resize, gentler non-ringing filters were all tried) if a shape looks "smeared" after the full pipeline; a spreading/dripping look that follows a *specific graphic's silhouette* (rather than a uniform halo at every opaque/transparent boundary) is almost always the flood-fill threshold eating into that graphic at step 3, not a resize artifact — diff the alpha channel right after step 3, before padding or resizing, against the source photo to confirm.
      6. Resize down to a sensible thumbnail resolution and PNG-quantize for file size.
      7. Verify by compositing the *final* file over both a light and a dark solid background *and viewing at 3-4× zoom*, not just at thumbnail scale — fringe and smear artifacts are easy to miss in a small full-image preview.
    - **Never bake in a fixed white or dark background** — always transparent, exactly like every hotlinked single-can `products[].img`. This lets `.thumb{background:var(--bg-surface-sunken)}` (theme-aware) show through around the product in both themes automatically, with no separate light/dark version to maintain. (A fixed-color version was tried for the Red Bull 24er and reverted after it broke the *other* theme — don't repeat that.)
    - **Verify, don't estimate, that the heart is clear**: sample the pixel directly under the heart's rendered position (map the heart's `getBoundingClientRect()` into the image's natural coordinates via the `object-fit:contain` scale/offset math, exactly like a single-can image would render) rather than judging by eye — several "should be fine" paddings turned out short by a few pixels when actually measured this way.

**Init sequence**: `loadDeals()` (at the very end of the script) calls `renderSkeleton(4)` synchronously to show loading placeholders, then `fetch("deals.json")`s the offer data. It waits for `Promise.all([fetch(...), delay(500)])` — the 500ms floor preserves the old simulated-loading feel so the skeleton doesn't just flash on a fast local response, while a genuinely slow/real request is still awaited fully rather than cut short. On success it populates `products`/`storeLogos`/`storeBranches`/`deals` and calls `finishInit()` (`render()` + the other setup calls that used to sit directly in the old `setTimeout`). On failure (network error, non-2xx, unexpected JSON shape) it calls `showLoadError()` instead, which renders a dedicated `.empty`-style error card with a "Erneut versuchen" button wired back to `loadDeals()`. Keep this in mind when scripting/automating against the page — content is not present until the fetch resolves (~500ms locally).

## Datenquelle (deals.json)

Products, stores/branches, and offers are **not** embedded in `index.html` — they're fetched at runtime from [`deals.json`](deals.json) (same-origin, relative path, so it works locally and under a GitHub Pages project subpath). This is the seam meant for swapping in a real offer feed later: replace the file's contents (or point `loadDeals()`'s `fetch()` at a different same-shape endpoint) without touching UI code, as long as the shape below is respected. `deals.json` currently contains only hand-authored demo data (its own `_meta.description` says so explicitly) — no live retailer data is fetched.

**Shape** (see `deals.json`'s own `_meta.fields` for the authoritative, versioned copy of this):
- `products[]` — `{ id, name, brand, sizeMl, img }`. `img` is a hotlinked product-image URL (see **Images** above). Optional `isNew` (bool, default `false`) flags a product as newly added to the assortment — feeds the "Neuheiten" accordion in the mobile burger menu (`renderNewArrivals()` in `index.html`); has no effect on `deals`/offers.
- `stores{}` — keyed by retailer/chain name (the unified format's "Händler"). Each entry: `{ logo, branch: { address, geo, open, close, closedSun } }` — `branch` is the "Filiale" (address/hours/geo); `open`/`close` are hours in 24h float form (`7.5` = 7:30). One branch per chain in this dataset, not per-offer — a real multi-branch feed would need offers to carry their own `branchId`.
- `offers[]` — the unified **Angebotsformat**: `{ id, productId, store, regularPrice, offerPrice, pfand, packaging, distanceKm, validFrom, validUntil, link, lastCheckedAt }`, plus optional `units` (pack count, e.g. `4`/`6`/`12`/`24` for multipacks — `regularPrice`/`offerPrice`/`pfand` are then the total price/deposit for the whole pack, not per can) and optional `priceHistory` (see **Preisverlauf** below). `productId` → `products[].id`; `store` → a `stores{}` key. `pfand` (EUR) and `packaging` ("Dose"/"Flasche") are the deposit/packaging fields; `validFrom`/`validUntil` (`YYYY-MM-DD`) are the "Angebotszeitraum"; `distanceKm` is the "Entfernung".
- **Öffnungsstatus is intentionally *not* stored** — `isStoreOpenNow()` computes it client-side from `stores{}.branch` (open/close/closedSun) against the current time on every render, so it can never go stale the way a snapshotted boolean would.
- **Preisverlauf**: each `priceHistory[]` entry is a *dated* point — `{ date: "YYYY-MM-DD", price, retailer?, deposit?, unitPrice?, available? }` — not a bare number; the date is load-bearing (it drives the "Preisverlauf" sheet's swipeable day-by-day carousel, see `renderDayCarousel()`/`buildDayCardHtml()` in `index.html`), not decorative. Only `date` and `price` are required — `normalizePriceHistory()` fills in any missing optional field from the parent offer (`retailer`→`store`, `deposit`→`pfand`, `unitPrice`→derived from `price`/`totalMl`, `available`→`true`), so a future real feed can supply minimal `{date, price}` pairs. A legacy plain `number[]` (no dates) is still accepted for backward compatibility — dates are then inferred by counting back from `DEMO_TODAY`, but new data should always use the dated object form. If an offer omits `priceHistory` entirely, `buildDeals()` falls back to a synthetic 90-day series via `genPriceHistory()` (none of the current demo offers set `priceHistory`, so all history today is synthetic).
- `checkedMinutesAgo` ("Preis geprüft vor …", currently hidden in the UI) stays purely client-side, deterministic from the offer `id` via `hashStr()` — not sourced from JSON.
- `lastCheckedAt` (`YYYY-MM-DD`) *is* sourced from JSON — a purely manually-maintained editorial field, no automatic computation. Tapping the price on a deal card (`button.price`, `data-checked`) toggles a small anchored popover speech-bubble (`#pricePopover`, a single reused element repositioned per click via `showPricePopover()`/`togglePricePopover()`/`hidePricePopover()` in `index.html`) showing "Zuletzt geprüft · …" formatted via `formatSingleDate()`. Always positioned directly below the clicked price (never above, so it can't cover the product image/name higher up in the card) — horizontal position computed from the clicked button's `getBoundingClientRect()` and clamped to the viewport; the popover closes on an outside click, on re-clicking the same price, or on scroll/resize. Falls back to `LAST_CHECKED_FALLBACK` (`DEMO_TODAY_STR`) if an offer omits the field.

**Loading states**: see **Init sequence** above for the loading/error mechanics. An empty (or all-filtered-out) `deals` array reuses the existing "Keine Angebote gefunden" empty state in `render()` — no separate "no data source" UI was needed.

## Progressive Web App (PWA)

The app is installable and works offline. This adds a few files alongside `index.html`, all wired with **relative** paths (no leading `/`) so it keeps working when served from a GitHub Pages project subpath (`https://<user>.github.io/<repo>/`), not just the domain root:

- `manifest.webmanifest` — name "CanSpot", `theme_color`/`background_color` matching the app's dark palette, `start_url`/`scope` set to `./`, and icon entries (see below).
- `icons/` — generated PNGs: `favicon-16.png`, `favicon-32.png`, `icon-192.png`, `icon-512.png` (purpose `any`), `icon-maskable-512.png` (purpose `maskable`, extra padding for Android's adaptive-icon safe zone), `apple-touch-icon-180.png`. All share the same mark — the can/location-pin glyph isolated from the logo SVG's standalone icon paths (i.e. the three `<path>` elements outside the lettering `<g>` in the header logo), white/`--brand-primary-blue` on a flat `--brand-primary-dark` background, rounded-square corners on every size except `icon-maskable-512` (full-bleed square; the OS applies its own mask) — matches the app's `theme-color`. Regenerated via a canvas-drawing script (`new Image()` from a data-URI SVG of just those 3 paths, drawn onto a `<canvas>` per size/corner-radius/mark-scale, exported with `toDataURL`) — there's no source vector file or generator script checked in, so redo this the same way if the mark changes again.
- `service-worker.js` — cache-first for same-origin requests, precaches the app shell (`index.html`, the manifest, `deals.json`, and the icons) on install, and falls back to the cached `index.html` for navigation requests when offline. It does **not** cache the hotlinked product/store images (external origins) — those still depend on network access, consistent with the existing hotlinking approach. Because `deals.json` is precached and the fetch handler is cache-first, an already-installed PWA keeps serving its last-cached offer data offline; a returning-online visitor also keeps seeing that cached `deals.json` until `CACHE_NAME` is bumped (see the bump note below) — this is deliberate, not a bug, but worth knowing when `deals.json` changes.
- In `index.html`'s `<head>`: `<link rel="manifest">`, favicon `<link>`s, `apple-touch-icon`, and the `apple-mobile-web-app-*` / `mobile-web-app-capable` meta tags for iOS/Android homescreen install. The service worker is registered at the very end of the main `<script>` block (after `loadDeals()` is kicked off), gated on `"serviceWorker" in navigator`, so it doesn't affect the existing init sequence or any UI behavior.
- **Mandatory cache-bump rule (no reminder needed):** `APP_SHELL` in `service-worker.js` lists every file the service worker precaches and serves cache-first (`index.html`, `manifest.webmanifest`, `deals.json`, all `icons/*.png`). Whenever a change touches the *content* of one of these files — including any edit inside `index.html`'s inline `<style>`, `<script>`, or markup, since it's the single-file app shell — bump `CACHE_NAME` in `service-worker.js` (currently `canspot-cache-v27`; next bump would be `v28`) as part of that same change, automatically, without being asked. The `activate` handler deletes old-named caches on its own once the version string changes. Without the bump, a returning visitor or already-installed PWA keeps being served the old cached files indefinitely — a `git push` updates GitHub Pages, but the change stays invisible on the live/test site until the cache is forced to invalidate. Only skip the bump for changes that touch nothing in `APP_SHELL` (e.g. only the standalone SEO landing pages, or `PROJECT_STATE.md`).

## Workflow: progress log & commits

Before treating any change as finished: check whether it touched a file listed in `service-worker.js`'s `APP_SHELL` (see **Progressive Web App (PWA)** above — in practice this means almost any `index.html` edit). If so, bump `CACHE_NAME` in the same change, so that a normal `git commit` + `git push` reliably updates the live GitHub Pages/test site instead of leaving visitors on a stale cached version. This applies automatically, every time, without the user needing to ask for it.

After every completed change, add a short entry to [PROJECT_STATE.md](PROJECT_STATE.md) (newest entry on top) covering: what was implemented, key decisions made, what's still open, and known bugs/next steps. `PROJECT_STATE.md` is the running progress log — `CLAUDE.md` stays reserved for durable project rules and technical notes and should not accumulate changelog entries.

After each meaningful milestone, create a git commit.
